# Contributing to KVM-X

Thanks for helping make virtualization work in more places. The most valuable
contribution is **a report from a platform we have not seen** (see below), then
fixes for the platforms we already know about.

## Development setup

You need Go 1.24+, Python 3 (fixtures), and optionally `qemu-system-x86` and Docker
for the integration tests. kvmx has **no third-party Go dependencies**; please keep
it that way unless there is a very good reason.

```bash
git clone https://github.com/KVM-X/KVM-X && cd KVM-X
make build          # bin/kvmx, static
make test           # unit tests (no root, no KVM, no network)
make lint           # gofmt, go vet, golangci-lint, shellcheck
make integration    # real TCG boots + Docker; downloads ~22 MB once
```

## How the code is organised

| Path | Role |
| --- | --- |
| `internal/sys` | Everything read from the machine, behind an interface. `Host` is the real one, `Fixture` replays a recorded directory. |
| `internal/detect` | Facts → verdict (`HARDWARE-KVM`, `NESTED-KVM`, `SOFTWARE-EMULATION (TCG)`) and blockers. Pure functions over `sys.System`. |
| `internal/plan`, `internal/ops`, `internal/journal` | Blockers → reversible steps → executed with a journal. |
| `internal/qemu` | QEMU command lines, TCG profiles, KVM→TCG option rewriting, libvirt XML. |
| `internal/guest` | The pinned Alpine test guest and its initramfs overlay. |
| `internal/guide` | Instructions for things only the layer below can change (clouds, hypervisors, container flags). |
| `internal/cli` | Subcommands and shims. |

Rules of thumb:

* **Never report software emulation as KVM.** `detect` has an invariant test for this.
* **Every system change is an `ops.Op`** that describes itself exactly, is idempotent and
  returns an undo. No ad-hoc `exec.Command("sudo", ...)` in the CLI.
* Show before you change; `--dry-run` must be honest for every command.
* Detection must be testable without the real machine: add a fixture, not a mock.

## Adding or fixing a platform (fixtures)

Fixtures live in `testdata/fixtures/<name>/` and are generated by
`testdata/gen_fixtures.py`. To add one:

1. On the machine in question run `kvmx collect --out my-platform` (it records exactly
   the files and command outputs detection reads, with your username anonymised).
2. Add a scenario to `gen_fixtures.py` (or drop the collected directory in and add an
   `expect.json`) describing the verdict you expect.
3. `make fixtures && make test`.

## Pull requests

* Use [Conventional Commits](https://www.conventionalcommits.org/) (`feat:`, `fix:`, `docs:`,
  `test:`, `ci:`, `chore:`). Keep PRs focused.
* Add or update tests. Code touching detection needs a fixture; code touching system
  changes needs an `ops`/`plan` test using the temp-root `ops.Env`.
* Run `make lint test` before pushing. CI must be green.
* Documentation claims about performance must come from `kvmx bench` output; include the
  JSON in `docs/results/`.

## Reporting bugs

Use the issue templates. Please include the output of `kvmx detect --json`
(and `kvmx collect` output for platform problems). Do not paste secrets;
kvmx output contains none, but check before sharing.
